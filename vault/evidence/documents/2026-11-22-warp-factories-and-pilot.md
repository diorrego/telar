## What changes compared with our architecture

| Decision | What Warp documents | Adaptation to the pilot |
|---|---|---|
| Declare the flow | A Blueprint describes stages, owners, inputs, outputs, transitions and questions that stop the work. Conditions are expressed in natural language. [Blueprints](https://docs.warp.dev/factories/blueprints/) · [Gates](https://docs.warp.dev/factories/blueprints/gates/) | Define research, specification, implementation, verification and evidence delivery first. The actor, the action, the environment and the approved revision must match before producing effects. Branch protection and publishing permissions remain executable controls. |
| Coordinate and resume | A *work item* keeps its origin and the *foreman* delegates to workers. Factory MCP lets you send work, continue it locally and hand it back. Tool MCP servers serve a different purpose. [Overview](https://docs.warp.dev/factories) · [Factory MCP](https://docs.warp.dev/factories/factory-mcp/) | Open the first work item from the CLI. Use a common identifier in the thread, the plan, the branches and the QA record. In a test with Warp, rehearse the local handoff before developing our own client. |
| Work across several repositories | Warp documents a factory with coordinated changes across repositories. [Multi-repository guide](https://docs.warp.dev/factories/guides/multi-repository-factory/) | Keep the decision that agents also write to the vaults. An open PR, a localized fix and a passed functional test are different states. If two PRs are involved, QA identifies the exact combination it tested. |
| Choose execution | Hosted execution is the default path. *Managed self-hosting* requires Enterprise. A worker on your own infrastructure receives tasks over an outbound connection, while Warp keeps the control plane. Inference and transcript storage are configured separately. [Self-hosting](https://docs.warp.dev/factories/self-hosting/) | For fictitious material, the hosted flow can be evaluated if there is access. Before using real repositories, agree on which code, transcripts, attachments and metadata can leave the VPC. If fully in-house control is required, the alternative of local first and then ECS still stands. |
| Inspect the interface | The Computer Use recipe uses a verifier with Warp Agent in a hosted sandbox and publishes evidence of the interface change. [Computer Use](https://docs.warp.dev/factories/use-cases/computer-use-verification/) | Keep Playwright Test + Chromium and approved screenshots for reproducible regression testing in staging. Computer Use would be a complementary exploration on sample data if it yields useful findings. |
| Choose agents and credentials | Warp documents Warp Agent, Claude Code, Codex and Pi. For Codex with a cloud-managed secret, it documents a funded API key. Authentication with a local subscription is a different mode. [Harnesses and authentication](https://docs.warp.dev/factories/harnesses/authentication/) | Keep our own adapter as an option for OpenCode, for authorized subscriptions and for the policy of compacting only when 50% of the window is exceeded. It remains to be tested whether a managed run exposes current usage, a compaction command and confirmation for the chosen provider. |
| Evaluate and improve | Scorers classify results. Benchmarks reproduce fixed tasks for **one worker** and compare configurations. The dashboard's autonomy metric counts merged PRs without a human push; they may have required approvals or clarifications. [Measurement](https://docs.warp.dev/factories/measure-and-improve/) · [Benchmarks](https://docs.warp.dev/factories/benchmarks/) | Use per-worker evaluations to change one variable at a time. Measure the full run separately: human hours, retries and total cost per accepted delivery. A scorer can propose a revision; changing the acceptance criterion requires a versioned human decision. |

## Vertical prototype before full infrastructure

The sample product is a **support agent for the software**. The factory is the process that researches, builds and verifies it. The [sample definition](../prototypes/warp/factory.yaml) and its three workers describe this flow. The configuration form on the CTO landing page is still our own conceptual schema. Warp's native format has its own schema. [Official syntax](https://docs.warp.dev/factories/factory-as-code/)

1. **Prepare the case.** Pin the revisions of a test application, an engineering vault and a QA vault. Include two queries: recovering access and handling a duplicate charge. Add an old guide that contradicts the current one. Product privately defines the expected behavior so it can evaluate whether the research tells the sources apart.
2. **Generate the specification before the code.** The foreman receives an open-ended request, consults the guides and publishes the diagnosis with verifiable references. It presents the scope, criteria and SHA of the plan. Product asks for a change and then approves the new revision. Capture both events. The first response, or an approval on the previous version, must not trigger implementation.
3. **Build and test.** The builder implements on a sample branch. The verifier checks that the agent answers by citing the correct guide and escalates the charge query. For interface changes, it runs the Chromium walkthrough and attaches desktop and mobile evidence. A reproducible failure sends the same work item back to implementation. A blocker is reported as pending. Limit retries and spend in whichever execution mechanism is chosen.
4. **Do the handoff.** The foreman returns the dossier to the channel with the commits, the environment and the verified criteria. A second session must be able to find the decision and the test by reading the vaults. The prototype ends in a reviewable delivery. A future production release will have its own authorization for the tested SHA and the target.
5. **Repeat and decide.** Repeat with a second work item, for example a guide that changes after the first approval. Compare the flow with the one a person assisted by a coding agent performs today. Keep the same inputs, revisions and criteria. Record human minutes, waiting time, compute and the cost of failed attempts. With two cases it is possible to decide what to fix; a general productivity estimate needs more observations. [Warp's incremental testing guide](https://docs.warp.dev/factories/guides/testing-and-tuning-your-factory/)

## Implementation and provider decision

**First test, available without contracting infrastructure.** Rehearse the Blueprint as a script with a local executor, fixtures and Git. Explicitly record who triggered each manual transition. This test makes it possible to evaluate the inputs, outputs, decisions and the handoff. Durable automation and recovery after restarts will be demonstrated in the next phase. The definition was prepared, and its structure, along with the correspondence between stages and workers, was checked locally against the public v1alpha1 JSON Schema. The repository names are fictitious. It has not been run in Warp or in Woku.

**If Warp is tested.** Use its workers, routing and tracking as the owners of the execution of that trial. Verify access, permissions with distinct identities, provider spend, storage and resumption after an interruption. Compare them with the results of the local trial. Measure event deduplication and compaction with the edge cases of 50,000 and 50,001 tokens out of 100,000. These are compatibility tests of our model; the documentation examined does not establish those guarantees for every harness.

**If we build our own execution.** Keep the same flow and the same tests. The TypeScript coordinator applies authorized transitions, PostgreSQL keeps its state and the runner executes stages. Introduce Slack, pg-boss and Terraform/ECS when moving on to validate real channels, durable waits and VPC isolation. For each trial, an owner for dispatching work is chosen; duplicating dispatch in Warp and in our queue would make it hard to attribute retries and costs.

**Decision criterion.** Recommend managed Warp for the next phase only if the team accepts its data and cost model, and the trial demonstrates traceability, authorization on the correct version and independent verification. If the flow adds value but the VPC, identity, harness or compaction constraints remain open, keep the design learned and move forward with our own runner. Infrastructure, licenses and real access to Woku are still pending a decision.
